# pdstack v1 spec

This document is the build spec for pdstack v1. It is compiled from the tickets of the design map, [#1 pdstack v1 design](https://github.com/pdevito3/pdstack/issues/1), with every correction applied. Each section links to its tickets for the reasons. The tickets keep the history. If this spec and a ticket disagree, this spec wins.

`CONTEXT.md` defines the vocabulary. Read it first.

## 1. Scope

pdstack v1 is a Claude Code plugin. It sends a request to a playbook that plans, builds, verifies, and opens a PR. The content is harness-neutral markdown. Only the Claude Code adapter is built.

The standing rule for every local change: honor upstream as much as possible. A local change needs a reason that upstream cannot meet.

Out of scope for v1 (see the Out of scope section of [#1](https://github.com/pdevito3/pdstack/issues/1)):

- The review gate ([#14](https://github.com/pdevito3/pdstack/issues/14), [#15](https://github.com/pdevito3/pdstack/issues/15)). The quality loop is the last step before the PR.
- The Cursor cloud versions of the autopilots and orchestrate.
- benny automations.
- Adapters for other harnesses. The upstream Codex, Pi, and Copilot mapping files do not ship. A later move to Pi copies them again from upstream.
- pstack-claude sync tooling (`tools/sync.mjs`, `tools/substitutions.json`).
- Memory through Agent Beacon.
- Hook auto-routing. v1 has no hook.
- Remote agents, which includes a scheduled upstream review and the `schedule` wake for long runs.
- wayfinder in pdstack. The user keeps the global wayfinder skill.
- A pdstack bot UI.

## 2. Repo layout and the Claude Code adapter

Source: [#3](https://github.com/pdevito3/pdstack/issues/3), with the corrections on that ticket.

```text
.claude-plugin/marketplace.json     the repo is its own marketplace
.agents/skills/upstream-review/     project-local skill (section 12)
.github/workflows/                  CI and release-please
docs/spec/v1.md                     this spec
tools/                              repo maintenance scripts, not shipped
provenance.json                     pins and feed positions (section 3)
LICENSE, LICENSE-*, NOTICE.md       licenses and credits
README.md                           install and development instructions
plugins/pdstack/
  .claude-plugin/plugin.json
  models.json                       from pstack-claude, used by setup-pdstack
  agents/                           pdstack-agent and the review subagents
  packs/<pack>/                     standards.md, verification.md, forensics.md
  schemas/pdstack.schema.json       JSON Schema for .agents/pdstack.json
  scripts/run-external.mjs          runs a role on another model family
  skills/pdstack/                   the router (upstream poteto-mode)
    SKILL.md
    playbooks/<name>.md
    references/
    scripts/                        resume, worktree-audit, check-plan, watch-pr, orch
  skills/<leaf-skill>/
  skills/principle-<name>/
```

Rules:

- One tree. There is no generator. Harness-specific words (`${CLAUDE_PLUGIN_ROOT}`, Claude tool names in new text) stay out of skill bodies where upstream does not already have them.
- The router skill is named `pdstack`. `/pdstack <request>` starts it. `/pdstack:pdstack <request>` also works.
- Leaf skills keep their upstream names. Steps always call them as `pdstack:<skill>`. A user-level skill with the same name takes the bare `/<skill>`, so the namespace is mandatory.
- Leaf skills and principles have `user-invocable: false`. The slash menu shows only `/pdstack` and the direct-use skills, for example `setup-pdstack`.
- A skill that upstream marks `disable-model-invocation: true` (`wait-what`, `automate-me`) stays visible, because only the user can call it. The skill lint enforces this.
- The repo ships the license file of each upstream: `LICENSE-pstack` (cursor), `LICENSE-pstack-claude`, `LICENSE-mattpocock-skills`, and the third-party licenses that pstack-claude ships (`LICENSE-cursor-team-kit`, `LICENSE-thermos`). `NOTICE.md` credits all of them.

## 3. Provenance pins and feeds

Source: [#3](https://github.com/pdevito3/pdstack/issues/3) and [#17](https://github.com/pdevito3/pdstack/issues/17).

`provenance.json` at the repo root has three top-level keys:

```json
{
  "feeds": {
    "cursor/plugins": "<last reviewed sha>",
    "michael-denyer/pstack-claude": "<last reviewed sha>",
    "mattpocock/skills": "<last reviewed sha>"
  },
  "renames": [
    ["poteto-mode", "pdstack"],
    ["poteto-help", "pdstack-help"],
    ["poteto-agent", "pdstack-agent"],
    ["setup-pstack", "setup-pdstack"],
    ["pstack-models.md", "pdstack-models.md"],
    ["pstack:", "pdstack:"]
  ],
  "pins": {
    "plugins/pdstack/skills/deslop/SKILL.md": {
      "source": "michael-denyer/pstack-claude",
      "path": "plugins/pstack/skills/deslop/SKILL.md",
      "sha": "<full sha>",
      "status": "verbatim"
    }
  }
}
```

- `source` is `cursor/plugins`, `michael-denyer/pstack-claude`, or `mattpocock/skills`.
- `sha` is the upstream commit of the current local text.
- `status` is one of these:
  - `verbatim`: the file is equal to `git show <sha>:<path>`.
  - `renamed`: the file is equal to the upstream text after the `renames` table is applied in order. This status has no `why`.
    The check then removes each paragraph in the `drops` list. The list holds the upstream lines that point to the Codex, Pi, and Copilot mappings, which pdstack does not ship. A drop that no `renamed` file has is an error.
    A `renamed` pin can also have `"hide": true`. Then the check also adds `user-invocable: false` at the end of the frontmatter, if upstream does not have the key. This hides a leaf skill from the slash menu (section 2).
  - `modified`: any other change. `why` is required.
- Files that pdstack writes itself get no pin.
- `feeds` holds the last reviewed SHA of each feed. The upstream review moves these positions (section 12).

The `renames` table and the `renamed` status come from section 17.

## 6. Leaf skills, principles, and agents

Source: [#11](https://github.com/pdevito3/pdstack/issues/11) and [#5](https://github.com/pdevito3/pdstack/issues/5).

Copy all pstack-claude leaf skills, principles, and agents (section 4). Local changes:

1. `wait-what` replaces `bro`. The `/bro` links in `ketchup`, `pdstack-help`, and `pdstack-help/references/recipes.md` point to `wait-what`.
2. `reflect`, `reflect/references/synthesizer.md`, and `automate-me` read `writing-for-agents` by path, in place of `plugin-dev:skill-development`.
3. `principle-model-the-domain` gets one more rule: use the terms of the project glossary in code, and add new domain terms through `pdstack:domain-modeling`. The glossary is `GLOSSARY.md`, the current mattpocock name, or `CONTEXT.md` in a repo that has no `GLOSSARY.md`.
4. `principle-boundary-discipline` stays without change.

New principles, written by pdstack, with no pin:

- **`principle-functional-core`** (Architecture). Trigger: "Writing business logic, or a change that mixes decisions with I/O." Decisions live in pure functions, and a thin shell does the I/O. It points to `principle-boundary-discipline` for validation at the edges.
- **`principle-rich-domain-model`** (Architecture). Trigger: "Writing or changing a business rule for an entity or a domain concept." Behavior lives on the entity. Handlers and services do not change its state directly. Each change is a method with an intent name that enforces the rules. Domain concepts are value objects that validate on creation, not bare primitives. No public setters, and no collections that callers can change. Entity methods and value objects are the functional core. Handlers are the shell. Reference: `FullstackTemplate/docs/backend/domain-entities.md`.

The quality loop passes, the thermo skills, `recall`, and the fan-out skills (`swarm`, `arena`, `interrogate`, `reflect`) stay without change. Memory stays pull, not push.

## 7. Router

Source: [#18](https://github.com/pdevito3/pdstack/issues/18) and [#20](https://github.com/pdevito3/pdstack/issues/20).

The `pdstack` router is the pstack-claude `poteto-mode/SKILL.md`. The match rules, the todo list with `skip: <reason>` lines, the `figure-it-out` fallback, and the project playbooks under `.agents/playbooks/` stay without change. The harness mapping lines say that v1 supports Claude Code only (section 4). Local changes:

1. The `renames` table.
2. Non-negotiables, "Any code" line: add Functional Core.
3. Non-negotiables, prose line: `writing-for-agents` in place of `plugin-dev:skill-development`.
4. New Non-negotiables lines for stack packs:
   - Code in files that match the globs of a selected pack → read that pack's `standards.md` before you plan or write the code, and give its path to each delegate and reviewer.
   - Before Opening a PR → review the diff against `standards.md` of each matching pack. Fix each violation, or name the project doc that overrides the standard.
   - Verification → read `verification.md` of the matching pack, then the project `verify` skill, then `run`.
   - Runtime or trace forensics → read `forensics.md` of the matching pack.
   - Precedence: project docs win over packs, and packs win over principles.
5. The naming rule becomes: "name each principle and standard that shaped a decision".
6. New Subagents rule: every pdstack worktree goes in `worktreeHome` from `.agents/pdstack.json`, or in `../<repo>-worktrees` when the key is absent. This covers delegates, autopilot owners, orchestrate workers, runtime-forensics proofs, and the worktree of `opening-a-pr`.
7. New Subagents rules for model families (section 10): a role value `<family>:<model>` runs through `scripts/run-external.mjs`. With only Claude, a role that asks for a different family uses a different Claude model and states the gap in one line.

The router does not load stack packs at the start. Each step reads the file that it needs.

## 8. Stack packs

Source: [#12](https://github.com/pdevito3/pdstack/issues/12), with the correction on that ticket, and [#6](https://github.com/pdevito3/pdstack/issues/6).

Rules have three layers: principles, then stack packs, then project docs. The more specific layer wins. A standard that overrides a principle names that principle and gives the reason.

The first packs are `dotnet`, `react` (React with TypeScript), and `ios` (Swift and SwiftUI), at `plugins/pdstack/packs/<pack>/`. Each pack has three files and states its file globs:

- `standards.md`: each standard gives the rule, why it matters, and how a reviewer can see a violation.
- `verification.md`: how to prove a change on the real surface of the stack, for example an Aspire app host or the iOS simulator.
- `forensics.md`: for each symptom (CPU, leak, hang, visual glitch), the capture tool, the file format, the converter to a searchable form, how to resolve symbols to file and line, and the proof method on a live process.

Sources for the content:

| Pack | Sources | Notes |
|---|---|---|
| `dotnet` | `FullstackTemplate/docs/backend/` | Holds the Rich Domain Model patterns: private setters, static `Create` and `Of` factories, `ValidationException` with request field names, value objects backed by a private `SmartEnum`, guards, and domain events. Forensics: `dotnet-trace`, `dotnet-counters`, `dotnet-gcdump`, `dotnet-dump`, Hot Reload. |
| `react` | `FullstackTemplate/docs/frontend/` | Points to the `typescript-best-practices` leaf skill. Forensics: Chrome DevTools and CDP. |
| `ios` | `AGENTS.md`, `CONTEXT.md`, and ADRs of FableFrog and journal-recall-ios | Forensics: Instruments, `xctrace export`, `spindump`, `.memgraph`, `lldb`. |

A project cannot add its own pack in v1. Rules for one project go in the project docs.

## 9. Project config

Source: [#13](https://github.com/pdevito3/pdstack/issues/13), with the corrections on that ticket.

The project config is `.agents/pdstack.json`, committed to the repo. The plugin ships its JSON Schema at `plugins/pdstack/schemas/pdstack.schema.json`. Every key is optional. If the file is absent, all defaults apply.

| Key | Type | Default |
|---|---|---|
| `worktreeHome` | string | `../<repo>-worktrees` |
| `stackPacks` | array of `dotnet`, `react`, `ios` | `[]` |
| `planPath` | string | `~/.claude/orchestrate/<slug>/docs/` |

```json

  "worktreeHome": "../FullstackTemplate-worktrees",
  "stackPacks": ["dotnet", "react"]
}
```

The tracker location is always `docs/agents/issue-tracker.md`. There is no SessionStart hook.

### setup-pdstack

`setup-pdstack` is pstack-claude `setup-pstack`, renamed. It keeps every upstream step except step 4 (the session hook) and the `session hook` line. It does these jobs:

1. Write the model sheet at `~/.claude/pdstack-models.md` and the `@` line in `~/.claude/CLAUDE.md` (upstream steps 1 to 3 and 5 to 8). The roles and the default panel stay as upstream has them. Section 10 adds model families.
2. Detect stack packs from marker files (`*.csproj`, `package.json` with `react`, `*.xcodeproj`). Ask for the worktree home and offer the default. Write `.agents/pdstack.json` with only the keys that differ from the defaults. Validate the file against the schema.
3. If `docs/agents/issue-tracker.md` or `docs/agents/domain.md` is absent, make it. This replaces `setup-matt-pocock-skills`.
4. Offer the verification skill and the formal verification skill (upstream steps 9 and 10).

A second run updates the files and does not duplicate them. The upstream `scripts/` (`check-sheet.sh`, `read-sheet.sh`, and the `.awk` files) get Node ports, because pdstack scripts are Node only. `copilot.md` ships without change.

## 10. Models

Source: [#20](https://github.com/pdevito3/pdstack/issues/20) and [#13](https://github.com/pdevito3/pdstack/issues/13).

The model sheet stays at the user level, in the upstream markdown format, at `~/.claude/pdstack-models.md`.

- A role value is a Claude slug (`opus`) or `<family>:<model>`, for example `interrogate reviewers: opus, fable, codex:gpt-6-sol`. Upstream lines stay valid.
- A family line holds a command template, for example `family codex: codex exec --model {model}`. The prompt goes on stdin.
- A step runs an external role with `node scripts/run-external.mjs --family <family> --model <model> --prompt-file <file>`, in the background, in the worktree of the role. The script runs the template and writes the output to a file. The agent reads that file. There is no Claude wrapper.
- `setup-pdstack` looks for known CLIs on `PATH` (for example `codex` and `gemini`) and offers each one as a family. It gets the model list from the CLI, or asks the user. It makes one short test call for each model before it writes it. It offers to put a new family in the roles that ask for a different family. Run `setup-pdstack` again to add a family later.
- With only Claude, roles that ask for a different family (eval judge, `show-me-your-work` audit, arena cross-judge, orchestrate verifier) use a different Claude model from the one that did the work. The reply states the gap, for example "No other family is configured. The judge was `fable`."

## 11. Quality loop

Source: [#16](https://github.com/pdevito3/pdstack/issues/16).

The quality loop is the name for the upstream passes at their upstream points. Nothing gets a local change.

- `deslop` before each commit (one pass).
- `no-comments` before review (runs again one time, fails on a second rejection).
- `unslop` on every prose surface, plus `technical-writing` for docs, PR text, and commit text.
- `interrogate` when the design is contested, and in the PR subagent (one pass, applies no changes).

`thermo-nuclear-review` and `thermo-nuclear-code-quality-review` stay on-demand leaf skills. `thermos` runs both. No playbook calls them. `simplify` is not added. There is no second verification after the loop.

## 12. Upstream review

Source: [#17](https://github.com/pdevito3/pdstack/issues/17).

A project-local skill at `.agents/skills/upstream-review/`, run by hand. `tools/upstream-diff.mjs` collects the data.

1. The script diffs each feed from its position in `feeds` to `HEAD`, for the upstream folders that pdstack copies from. It lists changed, new, and deleted files.
   - cursor/plugins is the feed of intent. Every cursor change is listed.
   - pstack-claude is the feed of translation. For each cursor change, the script shows whether a "Sync to upstream <sha>" commit translated it. pstack-claude changes of its own are listed with the reason from `tools/forks.json`.
   - mattpocock/skills is the feed for the three copied skills.
2. The script groups changes by upstream change (a commit or a release), not by file.
3. For each change, the agent gives a short summary, the pdstack files that it touches, its translation state, and a recommended verdict: adopt, adapt, or skip.
4. The user decides each verdict.
5. The agent applies the approved changes in one worktree and one PR, through `opening-a-pr`. A `verbatim` or `renamed` file is copied again from its source. A `modified` file gets its local change again on the new text, with `why` as the guide. Each touched pin gets the new `sha`. The PR body holds the table of decisions.
6. All feed positions move forward, also for skipped changes. A review that only skips still opens a PR. The CI provenance check proves the result.

## 13. Scripts and CI

Source: [#3](https://github.com/pdevito3/pdstack/issues/3).

- All scripts are Node `.mjs` with no dependencies, and they work on macOS, Windows, and Linux. They use `node:path`, and `node:child_process` with argument arrays, never shell strings. There are no bash, PowerShell, or awk scripts.
- Steps call `node "${CLAUDE_PLUGIN_ROOT}/scripts/<name>.mjs"` or the path inside the skill, as upstream does.
- A copied upstream script that needs Bun or bash gets a Node port, and its pin is `modified`. This covers `watch-pr/` (about 7,650 lines), `orch/` (about 4,150 lines), `check-plan.test.ts`, and the `setup-pstack` scripts.
- Tests use `node:test`.

CI runs on `ubuntu-latest`, `macos-latest`, and `windows-latest`. It does four checks:

1. Provenance: each `verbatim` file matches `git show <sha>:<path>`, each `renamed` file matches the upstream text after the `renames` table, each `modified` pin has a `why`, and each copied file has a pin.
2. Skill lint: valid frontmatter, a `name` that matches its folder, and no leaf skill call without the `pdstack:` namespace.
3. Version match between `plugin.json` and `marketplace.json`.
4. Unit tests for the plugin scripts and `tools/`.

## 14. Release

Source: [#3](https://github.com/pdevito3/pdstack/issues/3).

release-please reads conventional commits on `main`. It bumps `plugin.json` and `marketplace.json`, writes `CHANGELOG.md`, and tags a GitHub release. The changelog entry of a release PR can get more context before the merge. The first version is `0.1.0`. Versions stay below `1.0.0` until this spec is built.

## 16. Install

Source: [#21](https://github.com/pdevito3/pdstack/issues/21).

`README.md` must hold these instructions.

Install pdstack from the local repo:

1. Run `/plugin marketplace add ~/repos/pdstack`.
2. Install the `pdstack` plugin.
3. To get local edits, run `/plugin marketplace update`.

To work on pdstack itself, run `claude --plugin-dir ~/repos/pdstack/plugins/pdstack`. This loads the working tree directly.

An install from GitHub (`/plugin marketplace add pdevito3/pdstack`) stays possible for another machine.

Install-day checklist (phase 9):

1. Install from the local repo.
2. Run `setup-pdstack` once at the user level. It writes the model sheet and the `@` line.
3. Run `setup-pdstack` in FullstackTemplate, FableFrog, Cooklyn, BackWave, and journal-recall-ios.
4. In the dotfiles, remove all mattpocock skills except `wayfinder`, `grilling`, `domain-modeling`, `research`, `prototype`, and `wait-what`. Remove `skill-creator`. Keep `show-me`, `no-mistakes-pr-review`, and `pr-review`.
5. Point the wayfinder skill at `setup-pdstack` in place of `setup-matt-pocock-skills`.

## 17. Spec decisions

The compile of this spec found these decisions. The user approved them on 2026-10-20. Corrections are posted on the tickets that they change.

1. **`writing-great-skills` is now `writing-for-agents`.** mattpocock/skills renamed it on 2026-07-23 (`1fc6573e`) and moved it to `skills/productivity/writing-for-agents/`. It has `SKILL.md` and `SKILL-MECHANICS.md`, and no `GLOSSARY.md`. pdstack copies the current upstream skill, to honor upstream. Every "read `writing-great-skills`" decision in [#10](https://github.com/pdevito3/pdstack/issues/10), [#11](https://github.com/pdevito3/pdstack/issues/11), and [#18](https://github.com/pdevito3/pdstack/issues/18) reads `writing-for-agents`.
2. **The `renames` table and the `renamed` status.** The decided renames touch about 50 copied files: the router folder, `poteto-help`, `poteto-agent`, `setup-pstack`, and the `pstack:` namespace. Without a rename status, each of these files is `modified`. Then CI cannot prove them, and each upstream review applies the renames again by hand. With the table, CI proves them, and the upstream review copies them again with no judgment. pstack-claude uses the same method (`tools/substitutions.json`) for its own renames.
3. **The `setup-pstack` scripts get Node ports.** They are bash and awk, and pdstack scripts are Node only ([#3](https://github.com/pdevito3/pdstack/issues/3)).
4. **`models.json` is copied.** `setup-pstack` and several skills read it.

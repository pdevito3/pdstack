### Find state machines

**You own the lifecycle map. Find each implicit state machine, prove every state has a way out, fix what is safe to fix, and make the machine explicit.**

An implicit state machine is one lifecycle, such as an upload, a job, a checkout, or a session, whose state, transitions, and owner are spread across the code instead of held in one place.

A guaranteed exit is a step out of a state that fires with nobody acting: a timeout, a sweeper, recovery after a restart, or a failure the code bounds with a timeout. A callback, a webhook, a poll result, and every user action, cancel included, may never arrive, so none of them is a guaranteed exit. Every non-terminal state needs a guaranteed exit. A state a user waits in also needs a cancel.

Every choice serves three readers. The user sees each state they can be in, with a way forward from it (**principle-experience-first**). The developer reads every state and transition of a lifecycle in one place. The agent finds the machine, its model, and the skill that checks it by the lifecycle's name. When two shapes serve all three equally, take the one with fewer states.

1. Inventory the lifecycles. Run the **how** skill over the area the user named, or the whole repo. Signals of an implicit machine: a status or phase value assigned in more than one module, booleans that only make sense together (`isLoading`, `hasError`, `isDone`), nullable timestamps that stand for phases (`startedAt`, `completedAt`), rows that wait in `pending` or `processing`, in-memory maps of work in flight, retry loops, timers, locks, and leases. Group the lifecycles by subsystem, the module or service where most of a lifecycle's state lives. With more than one subsystem, give each its own read-only subagent (**principle-guard-the-context-window**). Done when each lifecycle has a table with every state, including the states that live as flag combinations or null checks, every transition with its `file:line`, where the state is stored (memory, database, cache, client), its terminal states, and its spread. The spread is each module that writes the state, and the one owner that holds it, or `none`. A lifecycle that one owner already holds in one place is explicit. It goes through the exit audit and stays out of step 7.
2. Audit the exits. For each non-terminal state, record its guaranteed exit with its `file:line`, or `none`, and for a state a user waits in, its cancel. For restart recovery, name what a crash loses (memory) and what it keeps (persisted rows), and the startup code or sweeper that picks the kept state up again (**principle-make-operations-idempotent**). Also mark each transition that two actors can take at once, such as a retry that races a late callback, and each transition out of a terminal state. Done when every non-terminal state has an exit row, and every state with no guaranteed exit, or a waiting state with no cancel, is marked as a stuck-state suspect.
3. Model each subsystem with the **create-formal-verification-skill** skill, one project skill per subsystem, named for that subsystem. The subsystem's tables from steps 1 and 2 are the target, and the model is TLA+ with every property below, in place of the skill's own choice of one target and one property. The model holds:
   - each lifecycle's states and transitions from the inventory;
   - environment actions for failure, cancel, timeout, and crash, where a crash drops what memory held, keeps what is persisted, and runs the code's restart recovery;
   - fairness only on the guaranteed exits, so the model never relies on a callback, a poll, or a user;
   - a `Done` step in the end states, per the **statechart** skill, so `NoDeadlock` flags only non-terminal dead ends;
   - an invariant or action property for each rule the code promises, such as no step out of a terminal state, and that cancel is enabled in each state a user waits in;
   - a liveness property that each non-terminal state is eventually left.

   A violation is a finding, and its counterexample is the path to the stuck state. Done when each subsystem's generated skill has run, and each suspect from step 2 is either confirmed by a counterexample or cleared by a passing property.
4. Chart the most important user flows with the **statechart** skill. Rank the flows a user starts and waits on by how often users enter them and what a stuck state costs them, and chart them in that order. Cut one spec per flow from its subsystem model, small enough for the chart's state budget. Label states and steps in the user's words. Name the ranked flows you did not chart.
5. Sort each finding and each lifecycle that is not yet explicit into fix now or confirm first.
   - **Fix now.** The change fixes a bug or preserves behavior, touches only the one module that writes the state, and changes no public API or persisted shape. A missing timeout counts when the code already applies a timeout to the same operation or lifecycle. Take its duration from there, and name it in the reply.
   - **Confirm first.** Everything else, such as a timeout with no duration to copy, gathering a lifecycle that spans modules into one owner, changing persisted state or its migration, changing an API contract, or removing a state a caller can observe. Send the user the whole confirm-first list in one message, grouped by subsystem. Each item gives the current shape, the target shape, the counterexample or reader-load gain that motivates it, and its cost. The user named this gate, so it holds under any autonomy grant. Keep working on fix-now items while it waits.
6. Fix each fix-now bug, and each confirm-first bug once the user approves it, with steps 1, 3, 4, and 5 of the Bug fix playbook (`bug-fix.md`). The counterexample names the path. Replay it against the real code one step per action, in a test that drives the real store and the code's own timer and restart handling, with the clock faked where the code allows it. If a step cannot happen in the code, the model is wrong. Fix the model, rerun it, and drop the finding. Otherwise the test fails, then passes after the fix, and the property passes once the model gains the same exit in step 8. Bug fix step 5's skip clause does not apply.
7. Make each fix-now lifecycle explicit with steps 1, 5, and 6 of the Refactoring playbook (`refactoring.md`), and, with the same steps, each approved restructure that keeps behavior. An approved restructure that changes an observable state, an API contract, or a persisted shape goes through the Feature playbook (`feature.md`) instead, with a pin on everything except the approved change. The target shape:
   - one type that lists the states, where data that belongs to one state lives only in that state (**principle-model-the-domain**, **principle-type-system-discipline**);
   - one pure transition function from state and event to the next state or a rejection, which lists every state's exits (**principle-functional-core**);
   - one owner that applies it and persists the result, with each transition safe to repeat after a retry or restart (**principle-make-operations-idempotent**).

   Use the state machine library the repo already has. Without one, plain types and a function do the job.
8. Run the **maintain-formal-verification-skill** skill on each generated skill, so its model and coverage record describe the explicit machine. Done when every property passes, or the property that fails belongs to a confirm-first item the user has not approved.
9. Ship one PR per subsystem. In each, the formal verification skill lands first, then each failing repro before its fix, then the refactors, then the verification update from step 8 (**principle-sequence-verifiable-units**). Run **Opening a PR** for each.

**Reply:** each subsystem's lifecycles with their stuck states and what happened to each (fixed, confirmed by a model and waiting for the user, or cleared), each chart as a `mermaid` block with one line for each bug path, each generated skill with the command that reruns it, and the confirm-first list waiting for the user.
